# ADR-0020：单一维护者使用强密码、TOTP、恢复码与全局紧急开关

- 状态：Accepted
- 日期：2026-07-31
- 补充：ADR-0008、ADR-0011、ADR-0017
- 确认记录：GitHub Issue #31 中维护者于 2026-07-31 明确同意完整方案与安全审计补充

## 背景

P0 只有一名维护者，但后台可以看到大师核对凭证、修改不可变内容的生命周期投影并控制公开发布。单账号不等于低风险：密码泄露会直接影响全部内容；手机丢失可能使维护者无法下线问题内容；仅靠数据库手改又会绕过审计和并发保护。

P0 不收集普通用户账号，也没有可用于找回的短信或邮箱系统。方案必须在一个 NestJS 模块化单体与 PostgreSQL 内工作，不引入 Redis、身份云服务或第二个后台角色，并且允许服务器管理员在所有日常恢复材料同时丢失时执行可审计的最后恢复。

## 决策

### 首次初始化与密码

后台只有一个维护者账号，不提供注册、默认密码或 HTTP 初始化接口。账号名持久化为规范小写 ASCII；请求在账号限流与凭据校验前统一执行 NFKC、去除首尾空白并转为小写，保证两处使用同一个键。交互式 bootstrap 命令只允许在凭据库为空时运行，密码只从 stdin 读取；账号密码、TOTP 密钥和恢复码不得进入 CLI 参数、migration、环境示例或日志。

密码按 Unicode code point 计 16 至 128 位，使用 Node.js 内置 scrypt。部署时按实际服务器校准内存和耗时参数，并把算法版本、参数与随机盐同摘要一起保存，不能把参数散落为常量。凭据库已有唯一账号时，不存在的账号也使用该账号当前自描述的哈希参数执行等价工作量校验；尚未初始化时才使用固定假摘要。登录失败统一返回 `AUTHENTICATION_FAILED`，不暴露账号、密码或动态码哪一项错误。

### 两步登录与会话

登录分成两个一次性步骤：

1. 账号和密码校验成功后，签发五分钟有效的 256-bit 随机密码挑战；
2. 维护者提交挑战与六位 TOTP，服务端在 PostgreSQL 中原子消费挑战和 TOTP counter，然后建立会话。

TOTP 使用标准验证器兼容的 30 秒、6 位配置。允许时钟偏差不表示允许重放：最近接受的 counter 与凭据修订号一起持久化，登录、恢复完成、紧急停止和恢复公开内容共享同一防重放边界。刚用于登录的动态码不能立刻再次用于高风险操作。

随机会话令牌为 256-bit，只保存域分离 HMAC 摘要。生产 Cookie 固定为 `HttpOnly`、`Secure`、`SameSite=Strict`、`Path=/admin` 且不设置 `Domain`。会话闲置 30 分钟失效，绝对最长 12 小时；活跃访问只能推进闲置期限，不能延长绝对期限。退出立即注销当前会话，“注销全部会话”在 PostgreSQL 中原子撤销单一维护者的全部现有会话并作废尚未消费的登录挑战，不改变当前密码、TOTP 或未使用恢复码。

所有后台响应（包括认证、业务内容、核对凭证和错误）使用 `Cache-Control: no-store`，避免退出后从浏览器或中间层缓存读取敏感内容。后台写请求除会话 Cookie 外，还必须同时通过可信同源 `Origin` 和会话绑定的随机 `X-CSRF-Token`；CSRF 令牌只保存在运行中页面内存，不进入 localStorage、URL 或日志。Next.js 只提供同源 `/admin/api` 转发。

### 两阶段恢复与离线重置

首次初始化一次性展示十个高强度恢复码，服务端只保存域分离 HMAC 摘要，每个恢复码只能使用一次。日常恢复固定为两个事务阶段：

1. 正确恢复码被 PostgreSQL 原子消费后，立即提升凭据修订号，注销全部会话，并使旧 TOTP 与全部旧恢复码失效；服务端只签发十分钟有效、一次性的 256-bit 恢复挑战，同时生成待启用的新 TOTP 配置；
2. 维护者在挑战期限内提交新密码和待启用 TOTP 的动态码。服务端原子消费挑战与 counter，启用新凭据、建立新会话，并只在这次 `no-store` 响应中显示新的十个恢复码。

第一阶段之后即使浏览器关闭，也不能恢复旧凭据；只能用尚未过期的挑战完成第二阶段，或由服务器管理员执行离线重置。这是主动 fail closed 的取舍。

若密码、验证器设备和全部恢复码同时丢失，只允许拥有服务器与数据库权限的人运行交互式离线重置命令。命令同样只从 stdin 读取秘密、提升凭据修订号、注销全部会话并追加安全事件，不能增加短信、邮箱、默认口令或数据库手改后门。

### 密钥与持久化限流

密码、会话、密码挑战、恢复挑战和恢复码使用不同的域分离摘要或哈希用途。TOTP 密钥使用 AES-256-GCM 认证加密，保存密钥版本、随机 nonce 和 AAD；AAD 至少绑定账号与凭据修订号，防止密文被换到另一条记录。正式加密主密钥与 HMAC 密钥的托管和轮换由部署任务确定，不能复用数据库密码、Cookie 值或图片中转密钥。

登录和恢复在解析请求正文前先按可信请求来源执行 PostgreSQL 持久化限流；严格解析并规范化账号后、执行昂贵密码哈希或恢复码校验前，再执行账号级持久化限流。请求来源先用部署密钥转成单向指纹，不保存限流所需的原始 IP；账号不存在时也走相同账号限流与当前密码哈希工作量路径。单进程内存计数不能作为唯一保护。本地同源 Next 代理在进入受信 loopback rewrite 前删除客户端传入的 `Forwarded`、`X-Forwarded-*` 和 `X-Real-IP`，再由代理按实际连接重建；正式部署仍须在 Issue #34 冻结入口代理 CIDR 与覆盖转发头的规则。

### 安全记录

登录密码校验、TOTP 登录、退出、全部注销、恢复两阶段、离线重置、限流、CSRF 拒绝、紧急停止和恢复均追加安全事件，至少保留 365 天。事件包含时间、动作、成功或拒绝、明确填写的高风险原因、请求编号、单向来源指纹和经过白名单截断的浏览器摘要；不得记录密码、TOTP、恢复码、挑战、会话、CSRF 原文、原始 IP、完整 User-Agent 或内部异常文本。

维护者登录后可以按时间倒序查看这些关键记录。安全事件为追加记录，后台不能编辑或删除。

### 全局紧急停止

PostgreSQL 保存唯一的全局公开内容开关和单调递增修订号。停止与恢复都必须同时提供：

- 有效后台会话、可信同源 `Origin` 与会话 CSRF 令牌；
- 未使用过的 fresh TOTP；
- 停止时精确短语“停止全部公开内容”，恢复时精确短语“恢复全部公开内容”；
- 非空原因；
- 当前开关的 `If-Match`；
- 同一业务重试复用的 `Idempotency-Key`。

更新开关、消费 TOTP counter、保存幂等结果和追加安全审计必须在同一个 PostgreSQL 事务中完成。开关关闭后，源站对今日内容、指定日期内容、穿搭详情、海报创建、海报查询和受控海报素材读取统一 fail closed，返回 `503 PUBLIC_ACCESS_STOPPED`；帮助说明、反馈和健康检查继续可用。恢复全局开关不会跳过每个内容版本原有的发布、审核和素材安全门槛。

源站无法召回已经下载或被外部转发的副本，也不能仅凭本地测试证明 CDN 已清除。正式 CDN 的 `purge/deny` 联动、传播时间和中国大陆网络表现由 Issue #34 在真实部署环境验证。

## 影响

- 后台实现必须先建立认证领域模块和版本化迁移，所有既有后台写接口都要接入统一会话、Origin 与 CSRF 守卫；
- OpenAPI 冻结登录、恢复、会话、安全记录和紧急控制的接口与稳定错误码，前后端不得自行发明第二套类型；
- 恢复第一阶段会立即使旧凭据全部失效，维护者必须把新设置流程一次完成或使用离线重置；
- PostgreSQL 同时承担凭据修订、一次性消费、限流、幂等和审计一致性，不增加 Redis；
- 正式部署前必须配置独立密钥、可信代理与可信 Origin，演练恢复码、离线重置、全部注销和紧急停止；
- 本 ADR 解除后台认证方案的开发阻塞，但不解除域名、CDN、备份、真实微信访问或公开副本召回能力的上线阻塞。

## 未采用方案

- **仅密码登录**：单凭据泄露即可接管全部后台，且不满足高风险动作 fresh TOTP 要求；
- **短信或邮箱找回**：P0 没有用户通信身份系统，会新增第三方依赖、个人数据和新的接管面；
- **第三方身份云服务**：对单一维护者和当前模块化单体增加不必要的供应商边界；
- **只在内存中限流或保存会话**：多进程、重启和并发请求会绕过保护；
- **紧急时手工改数据库**：绕过二次确认、并发、幂等和审计，容易留下不一致状态；
- **宣称能召回全部已发布副本**：浏览器下载和外部转发不受源站控制，属于无法兑现的安全承诺。
