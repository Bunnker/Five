# 日历黄金数据生成依据

> 适用任务：Issue #7  
> 目标范围：`2026-01-01` 至 `2027-01-01`，首尾都包含，共 366 个 `fortuneDate`  
> 记录日期：2026-07-26

## 1. 这份文件解决什么问题

本文件规定 Five 的 366 日标准答案从哪里来、怎样生成、如何复核，以及什么情况下必须停止发布。

这里的“标准答案”至少包含：

- `fortuneDate`；
- 标准日干支及日支；
- 日五行和完整五档顺序；
- 生成规则版本和来源版本。

它不改变产品已经确认的 23:00 换日规则。系统必须先按 `Asia/Shanghai` 解析请求时间并得到唯一的 `fortuneDate`，再计算该日期的标准日干支。标准答案不接收未经解析的设备时间，也不能在得到 `fortuneDate` 后再次执行一次 23:00 换日。

农历年、月、日和节气属于页面展示字段，不参与 Issue #7 的核心五档标准答案。后续加入这些字段时，仍要使用本文件记录的紫金山天文台资料单独核对，不能反向修改日干支结果。

## 3. 权威规则

### 3.1 标准状态

国家标准全文公开系统将 GB/T 33661-2017 标为“现行”，发布日期为 2017-05-12，实施日期为 2017-09-01，主管和归口部门均为中国科学院。全国标准信息公共服务平台还记录了该标准在 2023-12-28 复审后“继续有效”，主要起草单位为中国科学院紫金山天文台：

- [国家标准全文公开系统](https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=E107EA4DE9725EDF819F33C60A44B296)
- [全国标准信息公共服务平台](https://std.samr.gov.cn/gb/search/gbDetailed?id=n4aXcLrEnvA%3D&mode=p)

若这两个官方页面以后显示标准被替代、修订或废止，现有黄金数据不得直接沿用，必须按第 7 节重新生成和复核。

### 3.2 日干支计算

紫金山天文台的官方解读明确给出：

1. 干支纪日从甲子到癸亥顺序循环，60 日为一周；
2. 循环参考时间为：北京时间公历 `1949-10-01` 对应的农历日是甲子日；
3. 农历编算以北京时间为标准时间。

原始依据：

- [紫金山天文台《国家标准〈农历的编算和颁行〉解读材料》](https://pmo.cas.cn/xwdt2019/kpdt2019/202203/P020240201504886119982.pdf)

Five 的标准日干支必须由下列确定性步骤产生：

```text
输入：已经解析完成的 fortuneDate
dayOffset = fortuneDate 与 1949-10-01 的公历自然日差
ganzhiIndex = ((dayOffset % 60) + 60) % 60
输出：六十干支表中 ganzhiIndex 对应的日干支
```

两次取模用于保证早于锚点的负偏移也得到 `0..59` 的稳定索引。

### 3.3 农历展示字段

官方解读说明的主要编排规则包括：

- 以北京时间为标准时间；
- 朔日是农历月的第一个农历日；
- 包含冬至的农历月为十一月；
- 两个十一月之间出现 13 个农历月时，最先出现的不含中气的月为闰月；
- 十一月之后第 2 个不计闰月的农历月是农历年的起始月。

Five 的核心五行计算只依赖标准日干支。农历年、月、日和节气是页面展示字段，不能反向修改日干支答案。

### 3.4 本轮 366 日的官方对照物

紫金山天文台发布的《二〇二六年日历资料》注明按 GB/T 33661-2017 编制，并列出了：

- 2026 年 1 月至 12 月每天的公历与农历日期；
- 2027 年 1 月和 2 月每天的公历与农历日期；
- 2026 全年及 2027 年 1 月、2 月的节气；
- 2026 全年及 2027 年 1 月、2 月的朔、望、两弦时刻。

因此，本轮 `2026-01-01..2027-01-01` 的 366 个日期都在同一份官方资料中，不需要拼接非官方来源。

本次下载到的官方 PDF 文件校验值为：

```text
sha256: 19509e6b1a2798f9d9a024332a15d1b2734012a50b90e3b452d793bf0314e5d2
```

生成清单中必须同时保存原始链接和 SHA-256。以后同一链接下载到不同文件时，要把它当作来源变更处理，先人工检查差异，不能直接覆盖旧校验值。

## 4. `Asia/Shanghai` 的作用

IANA 的时区数据库面向软件实现者，提供民用时间的历史和当前 UTC 偏移规则。2026-07-26 查询时最新版本是 `2026c`：

- [IANA Time Zone Database 当前版本](https://www.iana.org/time-zones)
- [tzdb-2026c `zone1970.tab`](https://data.iana.org/time-zones/tzdb-2026c/zone1970.tab)
- [tzdb-2026c 亚洲区源码](https://data.iana.org/time-zones/tzdb-2026c/asia)

在 `zone1970.tab` 中，中国的 Beijing Time 对应 `Asia/Shanghai`；亚洲区源码也说明 Beijing time 由 `Asia/Shanghai` 表示，并记录当前规则为 UTC+08:00。

这只解决“某个时刻在北京时间是几月几日几点”的工程问题。IANA 不是农历或干支的权威来源，也不定义 Five 的 23:00 换日。生成记录必须写明使用的 tzdb 版本；本轮固定为 `2026c`。

这里的 `2026c` 是查询时 IANA 上游发布的参考版本，不等同于 Node.js 内置的实际运行版本。本轮固定的 Node.js `v24.14.1` 实际报告 `process.versions.tz = 2026a`、ICU `78.3`。答案文件会同时记录上游参考版本、Node 版本、实际 tzdb 版本和 ICU 版本，不能把其中一个冒充另一个。

## 5. `lunar-javascript` 的使用边界

### 5.1 固定版本和许可证

本轮交叉校验固定使用 `lunar-javascript@1.7.7`：

- [v1.7.7 Release](https://github.com/6tail/lunar-javascript/releases/tag/v1.7.7)，对应提交 `4c45a59`；
- [v1.7.7 `package.json`](https://github.com/6tail/lunar-javascript/blob/v1.7.7/package.json)；
- [v1.7.7 MIT License](https://github.com/6tail/lunar-javascript/blob/v1.7.7/LICENSE)。

该版本的包清单写明版本 `1.7.7` 和许可证 `MIT`，没有声明 `dependencies`，只有测试使用的 `devDependencies.jest`。因此可准确表述为“该版本没有声明运行时依赖”，不能把“当前没有声明”扩大成未来版本保证。

如果仓库、安装包或制品中分发该软件或其较大部分，必须按 MIT License 保留版权声明和许可证文本。即使只用于开发期交叉校验，也要在依赖清单中保留版本和许可证记录。

### 5.2 只用于离线交叉校验

生产后端的 `CalendarRuleEngine` 不得导入或调用 `lunar-javascript`。它只能出现在以下位置之一：

- 开发依赖；
- 黄金数据生成工具；
- 测试或独立校验脚本。

这样，即使该库以后升级、下架或计算结果变化，线上日干支仍由已冻结的国标锚点和 60 日循环确定。

### 5.3 日干支 API

官方 README 演示了从明确年月日创建公历日期，再转换为农历对象：

```js
const { Solar } = require('lunar-javascript');

const lunar = Solar.fromYmd(year, month, day).getLunar();
const ganzhiDay = lunar.getDayInGanZhi();
```

原始链接：

- [v1.7.7 README 示例](https://github.com/6tail/lunar-javascript/blob/v1.7.7/README.md)
- [官方干支 API 文档](https://6tail.cn/calendar/lunar.ganzhi.html)
- [v1.7.7 干支日源码](https://github.com/6tail/lunar-javascript/blob/v1.7.7/lunar.js#L943-L951)

库还提供 `getDayInGanZhiExact()` 和 `getDayInGanZhiExact2()` 两种晚子时口径；源码在 23:00 分支处理二者差异：

- [v1.7.7 23:00 分支源码](https://github.com/6tail/lunar-javascript/blob/v1.7.7/lunar.js#L743-L767)

Five 不使用这两个方法生成 366 日答案。原因是本产品已经在 `RequestContextResolver` 中把 23:00 后的时间解析为下一 `fortuneDate`；若再调用库内会推进日期的精确日柱方法，会造成第二次换日。交叉校验只把已经确定的 `fortuneDate` 年、月、日传给 `Solar.fromYmd(...)`，然后读取 `getDayInGanZhi()`。

也不要把宿主机器上的 `new Date()` 直接交给库。官方疑难解答强调调用方必须明确时区，而 `fromDate` 会读取 JavaScript `Date` 的本地字段：

- [官方时区说明](https://6tail.cn/calendar/faq.html)
- [v1.7.7 `fromDate` 源码](https://github.com/6tail/lunar-javascript/blob/v1.7.7/lunar.js#L13-L16)

## 6. 生成和校验清单

### 6.1 生成前

必须先固定并记录：

- 日期范围：`2026-01-01..2027-01-01`，首尾都包含；
- 预期记录数：366；
- `calendarRuleVersion`；
- 生成脚本的版本、文件清单和 SHA-256；入库后再由 Git 提交追溯；
- GB/T 33661-2017 标准状态；
- 紫台 2026 日历 PDF 链接和 SHA-256；
- IANA 上游参考版本 `2026c`，以及生成进程实际报告的 Node、tzdb 和 ICU 版本；
- 交叉校验库：`lunar-javascript@1.7.7`、提交 `4c45a59`、MIT。

缺少任一项时，不得把生成结果标成可发布的标准答案。

### 6.2 机器校验

生成过程至少要自动证明：

1. 日期连续、无重复、无缺口，第一天和最后一天正确，总数恰好为 366；
2. `1949-10-01` 计算为甲子日；
3. 相邻日期的干支索引是 `+1 mod 60`；
4. 任一日期加 60 天后得到相同日干支；
5. 366 日的国标锚点算法结果与 `lunar-javascript@1.7.7` 日期口径结果零差异；
6. 在进程时区为 `UTC`、`America/Los_Angeles` 和 `Asia/Shanghai` 时分别执行，输出文件字节完全一致；
7. 输出文件有独立 SHA-256，答案和边界数据在文件内也各有 SHA-256；
8. 以后加入农历展示字段时，再增加与紫金山天文台 2026 日历资料的逐日核对，不把它混入当前核心五档答案。

任何一项不满足都必须失败退出，不能只打印警告后继续。

### 6.3 23:00 边界单独测试

366 日表按 `fortuneDate` 记录每天的固定答案，不把时刻混进同一行。下列时刻另做边界测试：

- 22:59；
- 23:00；
- 23:59；
- 00:00；
- 00:59；
- 01:00；
- 月末、年末和闰日。

边界测试要证明：23:00 只把 `fortuneDate` 推进一次，跨过民用午夜后不再多加一天。

## 7. 人工门槛与更新规则

### 7.1 首次放行

机器校验全部通过后，仍需完成以下人工门槛：

1. 开发者检查来源链接、版本、许可证、日期范围和全部 SHA-256；
2. 开发者抽查首日、末日、每月月首、农历月首和所有节气附近日期；
3. 大师留下书面复核记录，至少覆盖连续 30 日；
4. 大师复核同时覆盖 22:59、23:00、23:59、00:00、月末、年末和闰日样本；
5. 复核记录写明大师称呼、核对时间、结论、备注和凭证引用；
6. 机器结果与大师样本零差异后，才可把该版本标为可用于内容发布。

若大师样本与权威算法冲突，处理方式是暂停发布、形成明确规则决策并升级 `calendarRuleVersion`。不得为了让样本通过而直接修改某一天的标准答案。

### 7.2 需要重新生成的情况

出现以下任一变化，都要生成一个新候选版本并完整重跑，不得原地覆盖：

- GB/T 33661-2017 被修订、替代或废止；
- 紫金山天文台更换对应年度日历资料，或同一 PDF 链接的 SHA-256 变化；
- `Asia/Shanghai` 的 IANA 数据变化会影响目标日期或边界解析；
- `calendarRuleVersion`、23:00 产品换日规则或六十干支表变化；
- 生成脚本或日期算法变化；
- `lunar-javascript` 版本变化；
- 已发布数据发现差异或来源记录不完整。

更新时必须保留旧版本、来源清单和差异报告。新版本仍需完成 366 日机器零差异和大师书面复核；升级交叉校验库本身不能自动改变权威答案。

## 8. 可直接采用的结论

- 核心日干支真源：GB/T 33661-2017 的 `1949-10-01 = 甲子日` 锚点与 60 日循环；
- 业务日期：由 Five 先按 `Asia/Shanghai` 和 23:00 规则得到唯一 `fortuneDate`；
- 官方展示对照：紫金山天文台《二〇二六年日历资料》，本轮 366 日范围全部覆盖；
- 独立校验：固定 `lunar-javascript@1.7.7`，只用日期口径 `getDayInGanZhi()`；
- 运行时：不依赖 `lunar-javascript`，不调用在线黄历 API；
- 放行：366 日机器零差异后，还必须完成连续 30 日及边界样本的大师书面复核。
